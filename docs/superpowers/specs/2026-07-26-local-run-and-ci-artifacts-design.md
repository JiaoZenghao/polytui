# Local Run Commands and CI Artifacts Design

## Goal

Make every PolyTUI implementation easy to run from the repository root and
publish each language's native build output as a GitHub Actions artifact after
a successful push to `main`.

This increment does not add new CLI or TUI behavior. It exposes the existing
entry points consistently and adds build distribution for the current
macOS-only milestone.

## Local command interface

The root `Makefile` will expose four independent targets:

```sh
make run-go
make run-rust
make run-typescript
make run-python
```

Each target runs the corresponding source implementation without installing it
globally. Callers may pass CLI arguments through the optional `ARGS` variable:

```sh
make run-go ARGS="--version"
make run-rust ARGS="--version"
make run-typescript ARGS="--version"
make run-python ARGS="--version"
```

The targets will use the repository's existing package-management boundaries:

- Go: `go run` from the Go module.
- Rust: `cargo run` with the Rust manifest.
- TypeScript: `pnpm` and `tsx` from the TypeScript project.
- Python: `uv run --project`, with no alternative Python package manager.

The Make targets do not silently install Go, Rust, Node.js, pnpm, Python, or uv.
The README will document prerequisites and the TypeScript dependency setup
required before the first local run.

## Build outputs

Each language keeps its native distribution model:

| Language | Build output |
| --- | --- |
| Go | `tar.gz` archive containing a macOS executable named `polytui` |
| Rust | `tar.gz` archive containing a macOS executable named `polytui` |
| TypeScript | Compiled `dist/` tree plus the package metadata needed to identify and run it |
| Python | Wheel and source distribution generated by `uv build` |

CI will stage outputs under language-specific directories before upload. The
staging layout prevents one language from overwriting another and makes missing
files a clear build failure.

Go and Rust will use one shared native-artifact build script. The
`build-native-artifact.sh` script will build the selected implementation and
create an architecture-qualified `tar.gz`. The companion
`test-native-artifact-archive.sh` script will extract that archive into a
temporary directory, verify that `polytui` remains executable, and run
`polytui --version`. Uploading the tar archive instead of the raw binary
preserves the executable mode inside GitHub's ZIP artifact.

Executable mode does not imply Apple Developer ID signing or notarization.
M1 artifacts remain unsigned, so Gatekeeper may require the user to approve a
trusted download through **System Settings > Privacy & Security > Open
Anyway**. The README will state this limitation. Automated signing and
notarization require Apple Developer credentials and belong to a separate
distribution milestone.

Artifact names will identify the project, language, macOS, and runner
architecture where relevant. GitHub Actions will perform the final artifact
archive operation.

## GitHub Actions behavior

The existing language-specific macOS jobs remain the primary CI structure.
Each job will keep its current validation steps and then build its native
artifact. Upload steps will run only when both conditions are true:

1. The workflow event is a push.
2. The pushed ref is `refs/heads/main`.

Pull requests continue to compile and test the implementations but do not
upload downloadable artifacts. A push to `main` uploads four independently
downloadable artifacts, one per language.

The lightweight validation job will run both contract validation and the CI
artifact-policy test. The four-toolchain black-box job will run both the
existing version-parity test and the Make run-target regression test. This
ensures pull requests cannot bypass the new local command or workflow policy
contracts.

Uploads will use the current official `actions/upload-artifact` major version,
`v7`, with:

- `retention-days: 30`
- `if-no-files-found: error`

The workflow keeps `contents: read`; artifact upload does not require repository
write permission. This feature uses GitHub Actions Artifacts only. It does not
create GitHub Releases or publish to GitHub Packages.

## Failure handling

- A test failure prevents the affected language job from reaching its build and
  upload steps.
- A build failure fails the affected language job.
- A Go or Rust archive that loses executable mode, cannot be extracted, or
  cannot report its version fails before upload.
- A missing staged output fails the upload step rather than emitting an empty
  artifact.
- Artifact upload is never attempted for pull requests.
- No generated build output is committed to Git.

Jobs remain independent: a successful language job may upload its artifact even
if another language job fails later. This preserves the current parallel CI
model and avoids reinstalling all four toolchains in a duplicated aggregate
job.

## Documentation

The README will replace the long-form local commands with the four root Make
targets, show `ARGS="--version"` as the current visible example, and explain
where artifacts can be downloaded from a successful `main` workflow run. It
will explain that Go and Rust downloads contain a `tar.gz` whose extracted
`polytui` is directly executable.

## Workflow policy validation

The workflow policy test will validate each language job independently instead
of relying on global counts. For every job it will check:

- the exact build or staging command;
- the exact staged output and upload path;
- the expected artifact name;
- the push-to-`main` upload condition;
- 30-day retention;
- failure when no file is found.

It will also verify that the validation job invokes the artifact-policy test
and that the black-box job invokes the Make run-target test. A configuration
placed under the wrong job or attached to the wrong upload step must fail the
test.

## Verification and acceptance criteria

The change is complete when:

1. All four `make run-* ARGS="--version"` commands print
   `polytui 0.1.0-dev.0 (<language>)` with the corresponding language name.
2. Existing `make test` checks remain green.
3. Go and Rust archives extract to executable `polytui` commands whose
   `--version` output matches the shared language-specific contract.
4. Workflow-focused tests validate every language job's exact build command,
   staged path, artifact name, `main`-push condition, 30-day retention, and
   missing-file policy.
5. Pull request CI runs both new regression scripts, performs tests and builds,
   and does not upload artifacts.
6. After merge, a successful `main` workflow run exposes four downloadable
   artifacts with the expected contents.

Local tests will cover the Make target contract before implementation. CI
configuration checks will cover the event gate and upload policy without
requiring a live GitHub Actions run for every edit.
